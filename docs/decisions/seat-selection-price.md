현재 구조(결정 기록 seat-hold-flow.md 포함)를 확인했고, 그 결정과 이어지는 선에서 설계를 정리해볼게.

1. 총 금액: 별도 state vs 파생값

파생값 계산을 추천. selectedSeatIds가 이미 단일 source of truth(결정 3)이고, ticketSeats도 이미 useQuery로 ReservationContent에 있으므로, 총 금액은 이 둘의 순수 함수입니다.

selectedSeats = ticketSeats.filter(s => selectedSeatIds.includes(s.id))
totalAmount = selectedSeats.reduce((sum, s) => sum + s.price, 0)

별도 useState<number>로 관리하면 문제되는 지점:

- 선택/해제할 때마다 수동으로 동기화해야 함
- 결정 6(HOLD 실패 시 toast + ticketSeats refetch)이 발생하면 금액 state도 별도로 리셋/재계산하는 코드가 또 필요해짐 — 두 군데서 같은 값을 다른 타이밍에 갱신하다 보면 어긋날 위험(전형적인 "state를 sync하려다 desync나는" 패턴)
- 계산 비용도 최대 4개 좌석 × 50개 배열 조회라 메모이제이션 없이도 무시할 수준 (필요하면 useMemo는 선택 사항이지 필수는 아님)

별도 state가 정당화되는 경우는 "서버가 할인/프로모션까지 반영한 최종 금액을 따로 계산해서 내려준다" 같은 케이스인데, 지금은 TicketSeat.price가 이미 좌석별로 존재하므로 해당 없음.

2. 선택/해제 로직 + 금액 계산 책임 분리

기존 결정 기록의 역할 분담(ReservationContent가 서버 통신·선택 상태 전부 소유)과 일관되게:

┌─────────────────────┬───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│ 컴포넌트 │ 역할 │
├─────────────────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ ReservationContent │ selectedSeatIds state 소유, 클릭 시 select/deselect 판단 + hold/release mutation 트리거하는 handleSeatClick 보유, selectedSeats/totalAmount │
│ │ 파생값 계산 │
├─────────────────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ SeatMap │ 클릭 감지만 하고 onSeatClick(seat)으로 위임. 스타일링을 위해 selectedSeatIds(또는 pending 상태)를 props로 받아 "선택됨" 표시만 함 — 선택 │
│ │ 로직/제한 판단은 하지 않음 │
├─────────────────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ SelectedSeatSummary │ 완전히 프레젠테이셔널. selectedSeats(또는 id+가격 목록)와 totalAmount를 props로 받아 렌더링만 함 — 계산 로직 없음 │
└─────────────────────┴───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘

이유: SeatMap이 좌석 렌더링에 isSelected 표시(범례에 이미 "선택한 좌석" 색상이 정의돼 있음)를 하려면 어차피 selectedSeatIds를 props로 받아야 하는데, 여기서 직접 "선택 가능한지/몇 석째인지" 같은 판단까지 하게 하면 로직이 두 군데로 쪼개집니다. ReservationContent 한 곳에서 판단하고, SeatMap/SelectedSeatSummary는 그 결과를 반영만 하는 게 기존 "이 화면의 상태는 한 컴포넌트가 소유" 원칙과 맞습니다.

3. 4석 제한 검증 위치

ReservationContent의 handleSeatClick 안, hold mutation을 호출하기 직전이 원칙적인 위치입니다. 상태(selectedSeatIds)를 바꾸고 실제 서버 요청을 트리거하는 지점이 여기이므로, "몇 석까지 허용"이라는 규칙도 같은 곳에서 게이트해야 합니다.

SeatMap은 이 규칙을 재구현하지 않고, ReservationContent가 계산한 isSelectionFull(또는 remainingSlots) 같은 boolean만 prop으로 받아서 "선택 안 된 나머지 좌석을 비활성화/흐리게" 같은 UI 힌트로만 씁니다. 판단 로직 자체가 두 곳에 따로 존재하면 나중에 어긋날 수 있어서, 계산은 한 곳(ReservationContent)에서만 하고 SeatMap은 그 결과를 소비만 하는 구조를 추천합니다.

⚠️ 짚고 넘어갈 엣지케이스 하나 — 이건 제가 판단할 문제가 아니라 결정 기록 4번(좌석별 pending 상태)과 얽혀 있어서 먼저 알려드립니다:

결정 1(비낙관적)에 따라 selectedSeatIds는 HOLD 응답이 온 후에만 갱신됩니다. 그런데 사용자가 응답이 오기 전에 연달아 여러 좌석을 클릭하면, 그 순간엔 아직 selectedSeatIds에 반영이 안 된 상태라 selectedSeatIds.length만으로 4석 체크를 하면 이미 나간(pending) 요청들을 세지 못해 5석, 6석 요청이 동시에 나갈 수 있습니다. 4석 제한을 정확히 지키려면 체크 기준을 selectedSeatIds.length + pendingSeatIds.size로 잡아야 할 가능성이 높은데, 이건 구현 시 확인이 필요한 지점이라 미리 알려드립니다.
